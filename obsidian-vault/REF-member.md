| 항목 | 상태 |
|---|---|
| 계정 생성 | 화면 없음, SQL로 생성(`build/nexus-create-user.sql`). `POST /users`는 로그인 없이 열림 |

| worker 접속 | `/worker` 무인증 — 아무 메인키로 등록 가능 (`REF-home-server.md` "코드 쪽 확인 결과") |

| worker 이벤트 | `output`·`status`·`editResult`·`screen`이 UID만 보고 처리 — 보낸 연결이 그 process의 인스턴스인지 검사 안 함 |

| 회원-Q5(관리자 판정) | `users.perms`에 `admin`. **회원이 0명일 때 가입한 첫 회원 = 관리자**, 그 뒤 = 일반 |

| 회원-Q8(실행 권한) | 장비 주인 + 그 장비가 지정된 폴더를 공유받은 사람만 |
| 회원-Q9(bcrypt 전환) | 같이 함. 로그인 때 옛 sha256 확인 -> bcrypt로 다시 저장. 아이디는 sha256 그대로 |
| 회원-Q10(장비 이름 관리) | 회원이 직접 등록, 전체에서 이미 쓰는 이름이면 불가, **이름 변경 없음** |
| 회원-Q11(인스턴스 구분) | 서브키 변경 대신 **인스턴스마다 라벨**(`worker_instances.label`) — 서브키는 `processes.device_key`·명부·worker sqlite에 박혀 있음 |
| 회원-Q12(닉네임) | 가입 폼 = 아이디 + 비밀번호만, **닉네임 = 아이디**(관리자 화면에서 아이디 확인용 임시 방편) |
| 회원-Q13(브랜치) | **집 서버 B 빌드와 같은 코드**에서 `feat/member` = `19cc8bd` + `feat/supervisor-move` 머지. supervisor-move는 회사 구형 worker 배포용이라 그대로 둠 |
| 회원-Q14(API 키 필요 여부) | **넣는다**(이름 등록 + 주인만 지정 + API 키 모두). 이벤트 검사(UID의 인스턴스 대조)도 넣음 |
| 회원-Q15(관리자 페이지) | **별도 페이지**에서 모든 회원의 장비·키·라벨 CRUD + 회원 상한·권한 |

| 회원-Q17(관리자 상한) | 관리자가 대신 등록할 땐 상한·등록 권한 무시 |
| 회원-Q18(주인 바꾸기) | **필요**. 옛 주인 폴더에 지정된 그 장비는 실행 막힘 |

## 배포 전 확인 (필수)
- **회원이 이미 있는 DB(빌드본·집 서버 등)에 배포하기 전에 반드시 "관리자로 지정할 회원"을 사용자에게 묻는다**(사용자 2026-10-26). SQL은 `00014_members.sql` 머리 주석
- supervisor env에 **`KEY_SECRET`** 추가(없으면 supervisor가 안 뜸) + 값 백업 안내(잃으면 키 보기만 불가, 접속 검증은 해시라 됨)
- worker는 **실행 파일 + env `API_KEY`** 둘 다 바꿔야 함 — supervisor-move 빌드 worker(2026-10-26 회사 배포)는 이 파트 배포 때 전부 재배포(사용자 이해함)
- 배포 순서: 각 회원이 "내 장비"에서 기존 메인키 등록(또는 관리자가 대신) -> 키를 worker env에 -> 새 worker 배포
