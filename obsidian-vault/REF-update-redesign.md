## 릴리스 구조 (확정)
장비(메인키)가 루트, 안에 빌드(버전). OS-CPU 분류 폐기(OS/CPU는 화면 표시용). 같은 메인키의 인스턴스는 같은 파일·`steps.json`을 받음.
```
common/<이름>/<버전>/        공용 묶음
<메인키>/<버전>/             장비 루트 > 빌드. steps.json에 "uses": ["nexus-worker@261103_a"]
```
- `common` = 공용 묶음, 빌드가 `steps.json`의 `uses`로 **명시 의존**. 배포 때 `uses`를 먼저 깔고 빌드 파일이 덮어씀. 쓰는 빌드가 잠기면 그 공용 버전도 같이 잠김(sha 유지)
- 잠금 단위 = `<메인키>/<버전>`, 성공 판정 = 그 메인키 인스턴스 중 한 대라도. 장비 루트는 updater 첫 접속 때 자동 생성(P1에는 updater가 없으므로 화면에서 메인키를 입력해 만들 수 있게)

## steps.json 구조 (확정)
```json
{ "deploy":   [ { "id": "stop", "script": "00-stop.sh" },
                { "id": "backup", "builtin": "backup" },
                { "id": "copy", "builtin": "copy" },
                { "id": "start", "script": "03-start.sh" },
                { "id": "verify", "script": "04-verify.sh", "timeout": "15m" } ],
  "rollback": [ { "id": "stop", "script": "00-stop.sh" },
                { "id": "restore", "builtin": "restore" },
                { "id": "start", "script": "03-start.sh" } ] }
```
- 단계 종류 = `script`(updater가 프로세스 실행, 종료 코드로 판정) / `builtin`(updater 프로그램 안 함수 호출, 셸 안 거침 -> OS 무관). `builtin`은 `backup`·`copy`·`restore`
- 복원을 스크립트로 쓰고 싶으면 `builtin` 대신 `script`. 환경변수 `BACKUP_DIR`·`NEW_FILES` 제공. 내장 `restore`는 기본으로 남김
- 되돌리기 버튼 = `rollback` 목록 실행. 실패 시 자동 실행은 기본 꺼짐, `"autoRollback": true`로 켬
- 단계 실패/timeout: 스크립트 프로세스를 자식까지 종료(Linux 프로세스 그룹, Windows 프로세스 트리), 배포 실패 표시

### builtin 동작
배포를 시작하면 updater가 빌드 파일(`uses` 포함)을 `staging/<배포 id>/`에 받는다.
| builtin | 하는 일 |
|---|---|
| `backup` | 덮어쓸 파일 중 `TARGET_DIR`에 이미 있는 것 -> `backups/<배포 id>/files/`에 복사, 없는 것 -> `new-files.txt`에 경로 기록, 배포 id·버전·시각 -> `manifest.json` |
| `copy` | `uses` 먼저, 그다음 빌드 파일을 `TARGET_DIR`에 덮어씀. 임시 이름에 쓴 뒤 이름 변경. 잠긴 파일은 기존 것을 `*.old-<시각>`으로 바꾼 뒤 씀. 지우지 않음 |
| `restore` | 백업 `files/`를 `TARGET_DIR`에 되돌리고 `new-files.txt`의 파일만 삭제 |
- `backup` 없이 `copy`만 개별 실행하면 복원 불가 -> 단계 로그에 경고(순서는 막지 않음)

## 웹 편집 (확정)
- 텍스트(스크립트·`steps.json`)는 관리자 화면에서 직접 작성·수정, 바이너리(exe 등)는 업로드 유지
- 테스트 흐름 = 수정 -> 저장 -> 단계 `실행`(기존 개별 실행) -> 로그. 잠그기 전에는 언제든 수정 가능(sha가 바뀜)
- 개별 실행 시 바뀐 파일만 먼저 전송(sha 비교)
- `.sh`는 LF로 저장. 실행 권한은 웹으로 만든 파일엔 없으므로 updater가 받을 때 부여하거나 `sh <파일>`로 실행(**미정**)
- **P1 = 원문 텍스트 편집 + 검증(줄 단위 오류 표시)**, `steps.json` 시각 편집 UI는 그다음. 저장 형식은 JSON 그대로, 폼이 모르는 필드는 보존

## updater 타일 페이지 (사용자 요청 11-02 — 설계-11 대체)
관리자만 접근하는 updater 타일 페이지. 각 updater를 파악하고, 그 안에서 빌드 > 형제 타일로 연다. **구조 이해는 확인 대기**(사용자가 "이렇게 이해했는데 맞는지"에 아직 답 안 함).
```
updater page (admin only)
+-- list: device(mainKey) > instance(subKey)     목록: online, 설치본, 마지막 접속
+-- common packs                                 공용 묶음
+-- device tile (mainKey)
     +-- builds: 261103_a, 261030_drag ...
          +-- Files tile        scope: common | mainKey | subKey
          +-- steps.json tile   P1 원문 편집, 이후 시각 UI
          +-- Script tile       텍스트 편집
          +-- Run/Log tile      배포·단계 실행·로그 (P2~P3)
```
- 타일 규칙은 기존 것을 따름: 종류 두 표(서버 `tileKinds`·프론트 `TILE_KINDS`) 같게, 열 때 연 곳 바로 뒤, 키의 `#` 처리(`KEY_RE`·`kindOf`·`KINDS`·`MemberPageKind`), 입력칸은 `Ct*`
- 제안(미확인): 공용 묶음은 빌드의 파일 타일에서 **읽기 전용**으로 보이고 "공용 묶음 열기"로 이동해 수정(여러 빌드에 영향이라 빌드 안 직접 수정 방지)
- **서브키 계층 (확정)**: 한 인스턴스에만 줄 파일. 합치는 순서 `common -> mainKey -> subKey`(뒤가 앞을 덮어씀). **P1에서는 자리만 만들고 구현은 나중**. 주의: 서브키는 supervisor 발급이라 `state.json`이 지워져 재발급되면 그 서브키 파일은 주인을 잃음. sha·잠금은 `<메인키>/<버전>` 안에 서브키 파일까지 포함해 계산
- `state.json`(제안한 이름) = updater가 설치된 PC에 두는 자기 기록(서브키·설치본 이름). 위치 = `TARGET_DIR` 밖 updater 전용 폴더. 형식(JSON/sqlite)은 P2에서 결정

## 파일 보관 결정 (11-02 오후, 진행 중)
- 보관 초안(이의 없음): 내용 = supervisor 서버 파일시스템(`<STORE>/common/<이름>/<버전>/` · `<메인키>/<버전>/` · `<메인키>/<버전>/@<서브키>/`), 메타(경로·크기·파일 sha·올린 사람·시각)·잠금·별칭 = DB. 폴더 sha는 파일 sha에서 계산. 스크립트·`steps.json`은 빌드 폴더 안의 평범한 파일
- **편집 이력 없음, 덮어쓰기만 (확정)**
- **잠긴 빌드: 수정 불가, 삭제는 가능 (확정)** — 서버 API는 잠긴 빌드의 쓰기만 거부하고 삭제는 허용
- **빌드 파일 한 번에 받기 (확정)** — 공용(`uses`)·`steps.json`·메인키·서브키 파일을 zip 하나로. **기본 = A(범위별로 그대로: `common/<이름>@<버전>/` · `main/` · `sub/<서브키>/`)**, **선택 = B(합친 결과: 공용 -> 메인키 -> 서브키 순으로 덮어쓴 최종 모양)**. 서버가 만들면서 바로 내려보냄(큰 바이너리 때문에 통째로 메모리에 안 올림)
- **삭제 규칙 (확정)**: 빌드 = 잠겨도 삭제 가능(페이지 안 확인 창), 삭제하면 서버 파일·재배포는 없어지고 배포 이력(이름·sha)은 남음, updater 백업·설치본은 영향 없음(복원 가능). 공용 묶음 = 쓰는 빌드가 하나라도 남아 있으면 삭제 불가, 쓰는 빌드가 없으면 잠겨 있어도 삭제 가능
- 미정: zip을 다시 올려 빌드를 만드는 "한 번에 올리기"가 필요한지(사용자 답 대기)

## DB 초안 (확정, 11-02 오후 — 컬럼 상세는 P1 착수 때 마이그레이션 번호와 함께)
supervisor PostgreSQL. 파일 내용은 서버 파일시스템 `UPDATE_STORE_DIR`, DB는 메타.
| 테이블 | 담는 것 |
|---|---|
| `updaters` | 메인키·서브키(PK)·별칭·메모·OS/CPU·설치 경로·설치본 이름(updater 보고값)·마지막 접속. online은 메모리에서 파생(관측용 명부) |
| `update_bundles` | 빌드와 공용 묶음을 한 테이블로: 종류(빌드/공용)·소유(메인키 또는 묶음 이름)·버전·폴더 sha·올린 사람·시각. (종류, 소유, 버전) 유일 |
| `update_files` | 번들의 파일 메타: 범위(메인키/서브키)·서브키·경로·크기·파일 sha |
| `update_uses` | 빌드가 쓰는 공용 묶음. `steps.json` 저장 때 다시 만듦. 공용 묶음 삭제 불가 판정에 씀 |
| `update_locks` | 잠금 기록(누가·언제·잠글 때 sha). 잠그기 때 빌드와 쓰는 공용 묶음마다 한 행. 해제 없음 |
| `update_deployments` | 배포 이력(인스턴스·시작/끝·결과·번들 이름·sha 사본). 번들 삭제돼도 이력이 남도록 연결을 끊고 사본을 둠 |
| `update_step_runs` | 단계 실행 기록(배포 중 또는 개별 실행·목록 deploy/rollback·단계 id·종류·결과) |
- 잠그기 가능 판정("현재 sha와 같은 성공 기록")은 **DB 함수 한 곳**(공유 판정 규칙과 같은 방식)
- **단계 로그 보관(확정)**: DB에는 요약(마지막 몇 줄)만, 전체 로그는 파일로 보관
