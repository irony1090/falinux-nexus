## 단계 개별 실행 (2026-10-30 확정)

| 항목 | 규칙 |
|---|---|
| `실행` 버튼 | **모든 단계 행**(수동 단계 포함) — 실패한 단계만 손으로 다시 돌리는 데 씀 |
| 잠금 판정 | 개별 실행 성공은 **"배포 성공"에 넣지 않음**. 잠금은 배포 1회가 끝까지 성공한 기록으로만 계산(`02-copy`만 돌려 성공해도 잠그지 않음) |
| 기록 | `deployments`와 **별도 행**(단계 실행 로그: 장비·단계·결과·시각)으로 남김 → 장비 이력에 "수동 02-copy"처럼 표시 |
| 순서 | **막지 않음** — 어떤 단계든 단독 실행 가능 |

## 잠금 (2026-10-30 확정: arch 단위 · "배포 완료"로 확정)

| 항목 | 결정 |
|---|---|
| 잠금 단위 | `os-arch` 폴더 하나(+ `common`) — 릴리스 전체가 아님 |
| 확정 동작 | **`배포 완료` 버튼**을 따로 둔다. 누르면 "이제 변경할 수 없습니다" 알림 |
| 잠기는 폴더 | 그 시점에 **성공 기록이 있는 arch 전부** + `common`(`common`은 하나라도 배포됐으면) |
| 성공 판정 | 그 arch 장비 중 **한 대라도 성공하면 성공** — 장비마다 환경이 달라 전체 성공을 기다리지 않음 |
| 테스트 배포 | 잠그지 않음. 몇 번을 해도 됨 |
| 추가 확정 | 남은 arch를 나중에 배포하고 `배포 완료`를 다시 누르면 그 arch가 추가로 잠김 |
| 성공 0 | `배포 완료` 비활성(잠글 대상이 없음) |
| 잠긴 뒤 | 파일·버전 이름 수정 불가 · **배포는 계속 가능** · 설명 글은 수정 가능 |

- 수정 가능한 동안은 그 내용을 가진 장비가 없으므로 위험이 0. 잠긴 뒤의 변경은 새 버전으로
- 잠금 판정은 `deployments`의 성공 행으로 계산 — 별도 상태 컬럼을 저장하지 않는다

## 되돌리기 (2026-10-30 확정: 역순 실행 아님)

**두 겹으로 나눈다.**

| 겹 | 무엇 | 누가 |
|---|---|---|
| 단계 안 | 실패한 **그 단계가 자기가 만든 변경만** 되돌림 | 단계 스크립트(`trap`) |
| 전체 | 이전 릴리스의 `steps.json`으로 **다시 배포** | supervisor -> updater |

| 단계 | 실패하면 남는 것 | 치우는 곳 |
|---|---|---|
| 00-stop | 서비스 정지뿐 | 치울 것 없음(다음 배포가 다시 시작) |
| 01-backup | 백업 파일 | 치울 것 없음 |
| 02-copy | 복사 절반 | **그 단계의 `trap`**이 백업 복원 |
| 03-start | 서비스가 안 뜸 | 이전 릴리스 재배포(00부터 다시) |
| 04-verify | 없음 | — |

```sh
#!/bin/sh
set -eu
DONE=0
# EXIT trap은 정상 종료에도 돈다 -> 성공했으면 되돌리지 않게 플래그로 막는다
trap '[ "$DONE" = 1 ] || cp -a "$BAK/." "$TARGET_DIR/"' EXIT
cp -a ./files/. "$TARGET_DIR/"
DONE=1
```

- `ERR` 대신 `EXIT` + 플래그를 쓰는 이유: `set -e` 밖의 명령 실패와 신호(`INT`/`TERM`) 종료를 같이 잡기 위해
- 전체 되돌리기는 "실행 취소"가 아니라 **직전 릴리스로 다시 배포**. 모든 릴리스가 이미 자기 설치 절차를 들고 있으므로 스크립트 추가 부담 0
- 직전 릴리스가 없거나 첫 배포가 실패 = `01-backup.sh`가 뜬 백업 복원이 유일한 길

기각한 안:

| 안 | 기각 이유 |
|---|---|
| 단계별 rollback 파일(`00-stop.rollback.sh` 짝) | 되돌릴 일이 있는 단계가 한둘뿐인데 단계 수만큼 파일이 늘고, 짝 빠짐 검사가 필요 |
| 한 스크립트 + `STAGE=rollback` 분기 | 같은 한계 + 한 파일에 두 방향이 섞여 읽기 어려움 |

### Windows 대응 (2026-10-30)

두 겹 구조는 OS 무관. 도구 이름만 대응된다.

| 되돌리기 요소 | Linux | Windows |
|---|---|---|
| 단계 자기 정리 | `trap ... EXIT` + `DONE` 플래그 | `try { } finally { if (-not $done) { ... } }` |
| 지우고 깔기 | `rsync -a --delete` | `robocopy /MIR` |
| 실패 시 중단 | `set -eu` | `$ErrorActionPreference = 'Stop'` + `exit $LASTEXITCODE` |
| 전체 되돌리기 | 이전 릴리스 재배포 | 같음 — 그 릴리스의 `steps.json`이 `.ps1`을 부를 뿐 |
| 실행 주체 | systemd 유닛 | 예약 작업(`nexus-update`, Job 탈출용) |

Windows에서만 다른 함정:

| 함정 | 내용 |
|---|---|
| `finally`가 안 도는 경우 | 프로세스 강제 종료·재부팅에는 안 돈다. Linux도 `SIGKILL`에는 `trap`이 안 돌아 조건이 같음 → 전체 겹(백업 복원·이전 릴리스 재배포)이 그 자리를 메움 |
| `robocopy` 종료코드 | **성공해도 1~7을 반환**. 실패 판정은 `8 이상`으로 해야 하고, 아니면 정상 복사가 실패로 보고됨 |
| 서비스 대응물 | systemd 유닛 자리에 예약 작업 → `TARGET_DIR` 밖 백업·복원 대상이 `schtasks`(`/Query /XML`로 뜬 뒤 `/Create`) |

되돌리기가 성립하려면 딸려 오는 조건:

| 조건 | 이유 |
|---|---|
| `02-copy.sh`는 **지우고 깔기**(`rsync -a --delete`) | 새 릴리스에만 있던 파일이 남으면 "이전 버전"이 아님 |
| supervisor 배포 전 **`pg_dump`** | worker 4개 · supervisor 15개 마이그레이션 모두 Down 절이 있지만 자동 실행하는 코드는 없음(goose는 up만). 되돌리기 = 옛 바이너리 + 옛 스키마 짝 |
| `TARGET_DIR` **밖**을 건드리는 단계 | 시스템 유닛·예약 작업·Caddy 설정 등. 그 단계의 `trap`이 그 파일도 백업·복원. 그래도 자동으로 안 풀리면 릴리스에 `90-rollback.sh`(`manual: true`)를 두고 손으로(자동 경로에 안 끼움) |

## 버전 표시 (2026-10-30 확정: 빌드에 박힌 env 값으로 고정)

**버전은 실행 중 읽는 env 파일로 바꿀 수 없다.** 빌드 시점에 바이너리에 들어간 env 원문에서만 읽는다.

| | 지금 | 확정 |
|---|---|---|
| 버전 출처 | `cmd/*/env` 첫 줄 주석(`# SUPERVISOR-DRAG-261029`) — 문자열로만 박혀 있고 읽는 코드 0 | **`//go:embed env`로 박힌 원문**(`cmd/supervisor/main.go:30`·`cmd/worker/main.go:26`)의 같은 줄을 읽어 고정 |
| 실행 시 `-env` 파일 | 로드해서 모든 값 덮어씀 | 버전만 **덮어쓸 수 없음**(파일에 다른 태그가 있으면 무시 + 경고 로그) |

| 순서 | 무엇 |
|---|---|
| 1 | `constants`에 `BuildTag()` — `envContent` 첫 줄에서 읽음(런타임 env 파일 안 봄) |
| 2 | env 로드 직후 `env.Version`을 그 값으로 덮어씀 |
| 3 | worker = `RegisterRequest.Build`(새 필드, 빈 값 = 옛 worker, `OS`와 같은 방식) · supervisor = 자기 API 응답에 실음 |

기각:

| 안 | 기각 이유 |
|---|---|
| `scripts/build.sh`의 `-ldflags -X main.buildTag=...` | 빌드를 build.sh로만 해야 값이 들어감. `go build`·`go run`은 빈 값 |
| `go:generate`로 상수 파일 생성 | 생성 파일이 저장소에 남아 **stale 위험**. `go build`만 하면 옛 값 |
| 실행 env 파일의 `VERSION`을 신뢰 | 파일을 고치면 버전이 거짓말함(사용자 지적) |

태그 줄은 **지금 첫 줄 주석 그대로** 쓴다(`build.sh`의 `tag()`가 이미 이 규칙 — 버전 문자열이 한 곳에만 존재).

## 내 장비 페이지 표시 · 배포 정보 타일 (2026-10-30 확정)

**인스턴스(`메인키#서브키`)마다 배포 정보 타일을 연다.** 같은 메인키가 두 기기를 가리킬 수 있어, 설치 경로·설치본은 장비 단위로 뭉치면 틀린다.

| 화면 | 누가 | 무엇 |
|---|---|---|
| 배포 페이지 | **관리자만** | 릴리스 올리기 · 배포 실행 · 잠금 |
| 배포 정보 타일 | **장비 주인 + 관리자** | 설치 경로 · 설치본 버전 · 실행 중 버전 · 최근 배포 이력 — 읽기 전용 |

| 값 | 무엇 | 출처 | 자리 |
|---|---|---|---|
| 설치 경로 · 설치본 버전 · updater(online·마지막 접속) | 그 기기의 디스크 상태 | updater 보고(`updaters`, 키 = `메인키#서브키`) | 배포 정보 타일 |
| **실행 중 버전** | 지금 돌고 있는 worker 프로세스의 빌드 | `RegisterRequest.Build` → 명부 `instances` | 인스턴스 줄(`subKey · os · …`) + 타일 |
| 최근 배포 이력 | 그 인스턴스에 배포한 기록 | `deployments` | 타일 아래 |

- **여는 곳**: 내 장비 페이지의 인스턴스 줄 끝 `배포 정보` 버튼 → 같은 페이지에 타일로 열림(`MemberPage` 타일 틀 그대로)
- **같은 컴포넌트·다른 플래그**: 배포 페이지 장비 타일과 같은 것을 쓴다. 아래 줄 버튼은 `canDeploy`(관리자)가 참일 때만 `콘솔`·`업데이트`가 보이고, 거짓(주인)이면 **아래 줄 자체를 숨긴다**(빈 40px 남기지 않음)
- 설치본 ≠ 실행 중이면 = **재시작이 필요한 상태**. 타일에 경고 표시
- 권한은 **서버가 판단**: 배포 API = 관리자, updater·배포 이력 조회 = 그 장비 주인 또는 관리자(남의 장비 조회는 거부)
- API: `useMemberDevice`의 인스턴스 항목에 `updater`(상태·경로·설치본·마지막 접속)를 합쳐 보낸다. 인스턴스 `Build`는 명부 행 필드로 추가
