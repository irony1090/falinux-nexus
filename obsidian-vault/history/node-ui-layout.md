## 2026-09-29(3) — 타일별 크기 조절(가로·세로 0.5/1.0) + 칸 채우기 배치 (코드 없음, 시안만)

## 2026-09-29(2) — 타일 순서 규칙 + 전체 재배치(reflow) + axis 기기별 파생 (코드 없음, 시안만)
- 사용자가 새 규칙 제시: 폴더에서 실행한 프로세스는 그 폴더 바로 뒤(기존 프로세스 뒤), 연 폴더는 그 뒤에 — "실행파일 우선, 폴더가 마지막". 예시(기본 / sup(1) / sup(2) / A / htop / 2F)로 설명.
- 여는 관계 트리의 깊이 우선 순회(프로세스 먼저)로 정리해 확인. 질문 3개로 갈린 부분 확정: **중첩 폴더 = 연 폴더 묶음 끝**(A가 X를 열면 2F보다 앞) / **Grid 반영 = 전체 재배치(reflow)**(4개씩 끊어 Grid 채움, 끼워 넣으면 뒤가 밀림) / **폴더 열기 = 둘 다 지원**(이름 클릭=타일 안 이동, 새 타일 버튼=새 폴더 타일).
- reflow가 2026-08-19 "axis/Band exec 시점 1회 결정·고정 저장" 결정과 충돌 → 추가 질문으로 **axis 기기별 파생** 확정(가로형 column / 세로형 row, 매 렌더). 저장 대상이 Grid 구조에서 **여는 관계 트리**(parent = 연 폴더 타일)로 바뀜. Grid 모양은 타일 수로 결정(1: A / 2: A|B / 3: A|B,C / 4: A,B|C,D).
- 시안 갱신: `TileOrder`(flatten/toGrids) 유틸 분리, 폴더 행에 "새 타일" 버튼, 타일마다 순서 번호·연 폴더 표시, 타일 순서 목록 패널. 사용자 예시 순서를 node로 돌려 일치 확인.
- 시안 가정(미확정): 폴더 타일 닫으면 그 폴더가 연 타일들이 닫힌 자리로 올라가 부모 소속.

## 2026-08-19(3) — 오버플로 Grid 페이지 크기/페이징 아이디어 제안 (코드 없음, 확정 아님)
- 요청: 각 Grid(2×2)가 헤더/푸터 제외한 뷰포트 100%를 차지했으면 함.
- 제안1: 앱 셸을 세로 flex column으로 짜서 `#Index{height:100%}`만으로 헤더/푸터 제외 크기를 자동 확보(JS 픽셀계산 불필요) — 단 헤더/푸터가 `position:fixed`(StickyBox)면 flex 흐름 이탈이라 안 통함, 그 경우 StickyBox의 `rootClient`/`maxClient`를 CSS 변수로 노출해 재사용 권장(새 ResizeObserver 안 만들기).
- 제안2: `#Index`+각 `tile-layout`에 `scroll-snap-type:x mandatory`/`scroll-snap-align:start`로 가로 스크롤을 페이지 단위로 스냅.
- **미확정** — 내일 이어서 결정(헤더/푸터가 실제로 fixed인지부터 확인 필요). 상세 → `REF-node-ui-layout.md` "오버플로 Grid 페이지 — 크기/페이징 아이디어" 절.

## 2026-08-19(2) — 구조 확정 시점 & 오버플로 처리 확정 (코드 없음, 순수 설계)

- **확정**: axis/Band 분할은 exec(분할 발생) 시점의 화면비로 1회 결정되어 "main" 구조로 저장 — 이후 어떤 기기에서 열어도 안 바뀜. 화면별 투영(짧은축 페이지네이션, 2026-08-10/12)은 이 고정 구조를 기기별 화면비로 재해석(표시 크기·페이지)할 뿐, axis 자체 재계산이 아니라는 게 명확해짐 — 기존 페이지네이션 설계와 모순 없이 들어맞음.
- **오버플로(2×2=4타일 초과) 처리**: 페이지네이션과 별개로, 새 `<tile-layout>`(Grid 인스턴스)를 옆에 추가해 가로 스크롤로 이어붙이는 방식 확정. 같은 세션 앞서 다룬 "가로 스크롤 활성화"(`#Index`에 `flex-shrink:0` 적용) 작업이 바로 이 오버플로 대응의 기반 구조였다는 게 이번에 드러남.

## 2026-08-12 — 레이아웃 데이터 모델 axis 일반화 (코드 없음, 순수 설계)
- 계기: "타일 레이아웃에 드래그 로직까지 구현해야 하는데 오픈소스가 없냐"는 질문에 Splitpanes/Golden Layout/Dockview 기각 결론(2026-08-10)을 재확인하던 중, 사용자가 "위: 가로로 넓은 타일 / 아래: 2개 나란히"(2×1 + 1×1 + 1×1) 같은 마스터-스택형 배치도 있지 않냐고 반문.
- 기존 확정 모델(`Grid.columns[Column.tiles]`)은 **루트가 항상 칼럼(좌우) 우선 고정**이라, 이 마스터-스택형(루트가 행 우선이어야 나오는 모양)이 표현 불가능하다는 걸 발견.
- **확정**: `Grid.axis: 'row'|'column'` 플래그를 루트에 추가해 일반화. 옛 `Column`(칼럼 전용 이름)은 axis에 따라 가로/세로 밴드 둘 다 될 수 있어 축-중립 이름 `Band`로 개명(가칭). `axis='column'`이면 기존 확정 모델과 동일(좌우 먼저), `axis='row'`이면 이번에 발견된 케이스(위아래 먼저)를 커버 — 두 방향 다 "한쪽 밴드만 추가분할"이라는 동일 규칙의 미러이므로 케이스 분기가 늘지 않음.
- **화면 크기별 투영도 재정리**: 기존 "짧은축=가로→페이지=컬럼단위 / 짧은축=세로→페이지=깊이단위" 규칙이 컬럼우선 전제였던 걸 발견, **primary/secondary 구조축 기준**으로 일반화("물리 짧은축에 대응하는 구조축을 페이지로 분리, 반대축은 동시표시"). 패킹 규칙(앞 슬롯부터 채우고 남는 슬롯은 빈칸)·최대 2페이지 상한 등 나머지는 변경 없음.
- 상세 → `REF-node-ui-layout.md`.
